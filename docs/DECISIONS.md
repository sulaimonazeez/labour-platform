# DECISIONS (append new ones; do not rewrite history)

Format: ID, decision, why, status.

D1. Drizzle ORM + postgres-js driver, schema in TypeScript, SQL migrations generated by drizzle-kit.
    Why: portable plain Postgres; migrations in the repo; works from Termux. Status: implemented.
D2. Supabase used as plain Postgres only. No Supabase Auth, RLS, or edge functions.
    Why: PRD role/object-level permissions belong in the backend; keeps the later VPS move to
    pg_dump + restore + a new connection string. Status: implemented.
D3. Two connection strings: pooled (6543, `prepare:false`, `max:1`) for runtime on serverless;
    session/direct (5432) for migrations, guards and seed. Status: implemented.
D4. Money as bigint minor units (`mode: "number"`) plus explicit currency char(3) on every
    financial row (PRD §45-46). Status: implemented.
D5. Service taxonomy keyed by `canonical_key`, with translations and synonyms in separate tables
    (PRD §24). Status: implemented.
D6. Double-entry ledger: `ledger_accounts` / `ledger_entries` / `ledger_lines`. Balances are never
    stored. A deferred constraint trigger enforces debits = credits per currency per entry at COMMIT;
    another enforces line currency = account currency (PRD §50). `ledger_accounts.owner_key` is a text
    key (`platform`, `user:<uuid>`, `provider:<uuid>`, `project:<uuid>`) to keep uniqueness simple.
    Status: implemented; balance trigger verified live.
D7. Integrity rules Drizzle cannot express live in `sql/guards.sql`, applied by `npm run db:guards`
    (idempotent). Append-only: activity_events, ledger_entries, ledger_lines, evidence,
    project_baselines, message_translations. Immutable: submitted quote versions and their line items;
    message original text/language/sender. Status: implemented.
D8. Task and payment state machines are deterministic transition tables in
    `src/engine/state-machines.ts`, typed from the DB enums (PRD §134-135). DB enums constrain values;
    the engine constrains transitions. Status: implemented, untested.
D9. Markets form a tree via `markets.parent_market_id` (global -> country -> region) for config
    precedence (PRD §128). PRD's `market_measurement_preferences` is folded into
    `markets.measurement_system`; `market_calendar_rules` into `markets.working_days/business_hours`
    plus `market_holidays`. Working days have no default; each market must set them (PRD §43).
D10. Quotes are versioned (`quotes` + `quote_versions` + `quote_line_items`); a version is immutable
     once `submitted_at` is set (PRD §53). `quotes.accepted_version` is an integer, not a FK, to avoid
     a circular reference.
D11. Chat is contextual: one conversation per (`context_type`, `context_id`); for the project context,
     `context_id` = project id (PRD §31-32). Translations stored separately with provider/model/
     confidence for provenance (PRD §29).
D12. Provider profile stores only approximate location (PRD §40).
D13. Hono as the HTTP framework (`@hono/node-server` for Node/VPS; a Vercel entry is still to be written).
     Input validation with zod. Status: implemented for auth routes. (Originally proposed in session 1;
     the owner's session 2 implemented it.)
D14. Auth: email + password, argon2id via `hash-wasm` (OWASP-minimum 19 MiB / 2 passes / 1 lane; WASM so it
     builds on Termux). Sessions are opaque random tokens sent as `Authorization: Bearer`; only the SHA-256 is
     stored (`sessions.token_hash`). Roles are resolved from `project_members` / `organisation_members`
     (authorization layer not built yet). Status: implemented, 12/12 tests.
D15. Supabase lockdown: because Supabase's Data API is installed, every one of OUR tables has RLS enabled and
     `anon`/`authenticated` grants revoked (`npm run db:lockdown`, idempotent). The script is scoped to the tables
     defined in `src/db/schema` (found via drizzle `is(x, PgTable)` + `getTableName`); it never touches other
     tables and no longer changes default privileges. The app connects as the database owner, which bypasses RLS.
     No RLS policies are written (D2). History: the first version acted on every `public` table and broke a
     neighbouring app that shared the database (see CHANGELOG). Status: implemented; scoped version not yet run.
D16. Guard tests: `src/db/test-guards.ts` exercises each trigger/constraint inside rolled-back transactions.
     Status: implemented; run output not yet recorded in the changelog.
D17. Rate limiting is DB-backed (`rate_limit_hits`, fixed windows, atomic upsert) because in-memory counters
     do not work across serverless instances. Limits: register 10 / 10 min / IP; login 30 / 10 min / IP and
     10 / 10 min / email (email keyed by SHA-256). `RATE_LIMIT_DISABLED=1` turns it off (used only by test:auth).
     Status: written in session 3, not yet run.
D18. CORS is opt-in via `CORS_ORIGINS`; default sends no CORS headers. Status: written, not yet run.
D19. Migrations are never hand-edited; schema changes go through `drizzle-kit generate`. Hand-written SQL for
     things Drizzle cannot express lives in `sql/guards.sql` (idempotent) and `src/db/apply-lockdown.ts`.
D20. Idempotency (`src/lib/idempotency.ts`): the `idempotency_keys` row is claimed INSIDE the business transaction and the
     response is stored in it, so effect + key + response commit or roll back together. Concurrent duplicates block on the unique
     insert, then replay. Scope is `<operation>:<userId>`. Request hash = sha256(method + path + key-sorted JSON body). Only 2xx
     results are stored (thrown errors roll the key back). `Idempotency-Key` is REQUIRED on create/convert endpoints (8-200 chars).
     Same key + different request = 422 `idempotency_key_reuse`. Replays carry `Idempotent-Replayed: true`. Keys never expire yet.
     Status: written, not yet run.
D21. Errors: `ApiError(status, code, message, details?)` can be thrown from anywhere, including inside transactions (rolls back);
     `app.onError` renders the standard `{ error: {...} }` body. Authorization failures are 404 when the caller has no relationship to
     the object (no existence leak) and 403 only when they are a member with an insufficient role. Malformed uuids are 404.
D22. `Executor` (`src/db/types.ts`) = drizzle `PgDatabase<PostgresJsQueryResultHKT, typeof schema>`: the shared type of `db` and
     transaction handles, used by authz/activity helpers. If typecheck rejects passing `tx`/`db`, fix this one type.
D23. Project currency is explicit at convert time (PRD §45) and must exist in `market_currencies` for the request's market. No default.
     Project timezone defaults to the owner's timezone, overridable. Converted projects start as `draft`; baseline version stays 0.
D24. Requests are visible to their requester only for now (ownership is part of the SQL `where`). `organisationId` on a request
     requires membership of that organisation (any role); finer org roles come with Phase 6.
D25. `test:requests` cleans up after itself via `DIRECT_URL`: in ONE transaction it disables only the activity_events append-only
     trigger, deletes rows belonging to `reqtest-*@test.invalid` users, and re-enables the trigger before commit (DDL is transactional).
     Dev databases only.
D26. Task transitions: `canTransition` (state-machines.ts) decides legality; a second rule decides who may do it by hand.
     Project managers (project_owner, project_manager) may only perform draft>ready, ready>blocked, blocked>ready and
     cancel from draft/ready/blocked. Every other legal move (offer, assign, accept, start, submit, approve, complete, dispute,
     cancelling work in progress) is `403 transition_reserved` and will be done by its own workflow (assignment, evidence,
     milestone, change request, dispute). Illegal moves are `409 illegal_transition`.
D27. Dependency edits lock the project row (`select ... for update`) so concurrent edits cannot jointly form a cycle.
     `dependsOnTaskId` from another project and unknown ids return the same 400 `dependency_invalid` (no existence leak).
     Dependencies are only recorded for now; they do not yet gate transitions (that comes with offers/assignments).
D28. Invitations (`task_invitations`, new table, reuses the PRD §95 `candidate_status` enum): a provider may only quote on a task
     they were invited to. The first invitation moves the task ready -> offered (this is the "offer" workflow D26 reserved); more
     providers can be invited while it is offered. Not invited = the task does not exist for you (404). A project owner or manager
     cannot be invited on their own project. Status: written in session 6, not run (needs `db:generate`, `db:migrate`, `db:lockdown`).
D29. Quote content: the server computes every line amount and the total (`src/engine/quote-math.ts`, BigInt, round half up to a minor
     unit; quantity max 3 decimals). Optional lines are priced but excluded from the total (PRD §52). Providers cannot add a
     `platform_fee` line (the platform adds that, disclosed). A client-sent total is rejected (strict schemas). Status: written, not run.
D30. One currency per project for now: quote currency must equal the project currency (400 `currency_mismatch`). Cross-currency quotes
     need the FX flow and `fx_conversions` (PRD §46). Status: written, not run.
D31. PRD §34 visibility: a member whose only roles are provider roles sees only tasks they hold an assignment on (project GET filters
     tasks and stages; task GET is 404 for other tasks and hides the dependency graph). Providers who are merely invited are NOT project
     members: they use `GET /providers/me/invitations`, which shows the task brief, project title/currency/timezone and nothing else.
     Awarding a quote adds the provider as a `provider` project member. Status: written, not run.
D32. Accepting a quote is ONE transaction: lock the task row, then the quote row (always that order); require task `offered`, quote
     `submitted`, project draft/active, version not past `valid_until`, provider active; then quote -> accepted (`accepted_version`),
     assignment created with status `offered` (the provider still has to accept it: next step), task offered -> assigned, provider joins
     the project, competing quotes close (private drafts -> `withdrawn`, others -> `rejected`, reason `task_awarded`), invitations settle
     (winner `assigned`, rest `expired`). The partial unique index on assignments is the last line of defence (409 `task_already_assigned`).
     Expiry is checked at accept time (409 `quote_expired`); no background job exists, so the `expired` quote status is unused for now.
D33. Quote lifecycle (`QUOTE_TRANSITIONS`): draft -> submitted (freezes the version) -> accepted | rejected | revision_requested.
     revision_requested -> draft by `revise`, which COPIES the latest version into version n+1 (history is never edited, PRD §53).
     Drafts are private to the provider: managers get 404 on a quote with no submitted version and only ever see submitted versions.
     Provider-only actions: create, PUT, submit, revise, withdraw. Manager-only: invitations, request-revision, reject, accept.
     Status: written, not run.
D34. Test cleanup now also removes quotes/assignments/provider profiles: inside the same single transaction it disables the two quote
     freeze triggers, deletes in dependency order (assignments, quotes), re-enables them, then deletes provider profiles. Dev databases only.
D35. Assignment response (`src/api/assignment-routes.ts`): only the provider who owns the assignment can respond (anyone else: 404).
     Lock order is task, then assignment (same as quote accept). Accept: assignment offered -> accepted, task assigned -> accepted.
     Reject: assignment offered -> rejected, task assigned -> offered (bidding reopens), the provider's invitation -> `declined`, and the
     provider's `provider` project membership is removed unless they hold another live assignment in that project (PRD §34).
     Optional `reason` is stored in the activity payload. Both are idempotent and emit `assignment.*` + `task.transitioned`.
     Status: written, not run.
D36. DECIDED by the AI (veto if you disagree): on reject the awarded QUOTE stays `accepted` (history is not rewritten; `accepted` is terminal in
     `QUOTE_TRANSITIONS`) and the other providers' invitations stay `expired`. The manager must invite providers again; a previously
     expired provider cannot be re-invited today (the invite route returns 409 `invitation_exists`). Follow-up: allow re-inviting `expired`
     invitations. Task start (accepted -> in_progress) is deliberately not here: it belongs with check-in/evidence.
D37. Milestones (`src/api/milestone-routes.ts`): created by project owner/manager only. Currency must equal the project currency (D30).
     `assignmentId` is optional (a project-level milestone is allowed) but, when given, must be an ACCEPTED/ACTIVE assignment of the same project
     (400 `assignment_invalid` for anything else, no existence leak). Milestones of one assignment cannot sum past the agreed quote total
     (409 `milestones_exceed_quote`, with `remainingMinor`); cancelled milestones do not count. The project row is locked while creating, so
     concurrent creates cannot jointly exceed the cap. Approver defaults to the project owner; a custom approver must be an owner, manager or
     finance approver MEMBER of the project (400 `approver_invalid`). Status: written, not run.
D38. Milestone lifecycle (`MILESTONE_TRANSITIONS`): pending -> submitted (provider, needs the evidence requirement) -> approved (only the named
     approver) | in_progress (approver requests changes, reason required) -> submitted again. Approval is NOT payment: `funded` and `released`
     are reserved for the payment flow (Step 3). Provider-only members get 404 (not 403) on approver actions, and non-owner providers get 404
     on milestones that are not theirs (PRD §34). `evidence_requirements` is stored as `{ minCount, kinds }`: submit counts evidence rows of those
     kinds attached to the milestone (409 `evidence_requirements_not_met` with `required/have/kinds`).
D39. Evidence METADATA endpoints (`src/api/evidence-routes.ts`): POST/GET `/tasks/:id/evidence`, POST/GET `/milestones/:id/evidence`. Writers: the
     provider holding the live assignment, or an inspector/supervisor member. Owners/managers cannot add evidence (403). Task evidence only while the
     task is accepted/in_progress; milestone evidence only before submission (409 `*_not_open_for_evidence`). Rules: file kinds (photos, video, document,
     receipt) need `storagePath`; every item needs a `storagePath` or non-empty `captureMeta` (4000 chars max); `storagePath` must start with
     `projects/<projectId>/` and contain no `..`; `fileSha256` is optional 64-hex; `capturedAt` cannot be more than a day in the future.
     The actual file upload (Supabase Storage vs S3-compatible, signed URLs) is still undecided: these endpoints only record metadata.
D40. Evidence rows are append-only in the database, so test cleanup now disables `trg_evidence_append_only` inside its single transaction and deletes
     milestones before assignments (milestones.assignment_id has no cascade). Same dev-only trick as D34. Retention/erasure (PRD §130-131) is still open.
D41. Task work lifecycle (`src/api/task-work-routes.ts`): provider `POST /tasks/:id/start` (accepted -> in_progress, assignment accepted -> active, sets
     `actual_start`) and `/submit` (in_progress -> submitted); manager (owner/PM) `POST /tasks/:id/request-changes` (reason required; submitted ->
     in_progress), `/approve` (submitted -> approved), `/complete` (approved -> completed, assignment active -> completed, sets `actual_end`).
     Lock order everywhere: task row, then assignment row. Non-assigned providers get 404, other members 403. Each step emits a specific event
     (`task.started|submitted|changes_requested|approved|completed`) plus `task.transitioned`. The generic `POST /tasks/:id/transition` still refuses
     all of these moves (reserved, D26).
D42. Dependencies now gate starting work: `finish_to_start` needs the other task `completed`; `start_to_start` needs it started. The other types
     (external, material, approval, payment) cannot be checked by the engine yet and do not block. A provider only gets `unmetCount`, never the ids
     of the blocking tasks (PRD §34).
D43. Task submit enforces `tasks.evidence_requirements` in the same `{ minCount, kinds }` shape as milestones (D38). There is NO endpoint to set it
     yet (task create does not accept it); tests set it directly in the database. Follow-up: accept it on task create/edit.
D44. A task cannot be completed while any milestone of its active assignment is not approved/released/cancelled (409 `milestones_open`). There is no
     endpoint to cancel a milestone yet. Completing a task does not touch payments: that is Step 3.


D45. Payments are provider-agnostic: `PaymentProvider` (src/payments/provider.ts), a sandbox adapter (tests/dev; refused when NODE_ENV=production) and a Paystack adapter (collection only). Chosen by PAYMENTS_PROVIDER.
D46. "secured" = gateway-verified AND ring-fenced in the ledger (protected_funds). It is NOT a regulated-escrow claim; legal review per market before real money (PRD §49).
D47. The gateway is never trusted for money: webhooks are signature-checked, then re-verified with the gateway; amount and currency must match; applying is idempotent (row lock + ledger idempotency key).
D48. Release is a separate explicit step after approval (POST /milestones/:id/release): DR protected_funds, CR provider_earnings, CR platform_fees (platform_fee_rules). Approval alone never moves money.
D49. NOT built: payouts (Paystack Transfers, provider bank details), refunds, dispute holds, reconciliation. Provider earnings stay in the ledger until payouts exist.
D50. Vercel deployment uses Vercel's zero-config Hono detection (checked against Vercel's Hono docs, Oct 2026): a file named `src/index.ts` that imports `hono` and default-exports
     the app. It wraps the real app (`src/api/app.ts`) with `app.route("/", api)` and re-adds the JSON notFound. `test:entry` proves 404/401/webhook error bodies survive the wrapper.
D51. The Node/VPS entry was renamed `src/server.ts` -> `src/node-server.ts` because Vercel selects its entry by the file names app/index/server (a listener-starting
     `server.ts` next to `index.ts` would make detection ambiguous). `dev`/`start` scripts point at the new file.
D52. `vercel.json` pins the function region to `dub1` (Dublin) to sit next to the Supabase database (eu-west-1, Ireland): requests run many sequential queries, so
     cross-ocean latency would multiply. Change it if the database region changes.

D53. Abandoned checkout (session 10). A payment still `pending` after PAYMENT_PENDING_TTL_MINUTES (default 30) is "stale". Expiry is LAZY: it is
     checked only when someone tries to pay the milestone again, never by a background job. Before closing a stale payment we ASK THE GATEWAY: paid ->
     secure it and answer 200 `{alreadyPaid:true}` (no second payment); amount mismatch -> 200 `{needsReview:true}`; otherwise pending -> `failed` (event
     `payment.expired`) and a NEW payment with a fresh reference is created. These return 200, not an error, so the transaction commits what was recorded.
     LATE SUCCESS: if a `failed` (expired) payment turns out to have been paid (webhook or verify), the money is booked in the ledger as SUSPENSE
     (`adjustments` account `suspense:payment:<id>`, key `payment:<id>:late_success`), event `payment.late_success`; it does NOT fund the milestone and does NOT
     become protected funds. The payment stays `failed`. A human refunds or reassigns it (there is no refunds endpoint yet), surfaced in GET /admin/attention.
D54. Refund / dispute / chargeback webhooks are LOGGED, not applied: event `gateway.event_received` (deduped by SHA-256 of the raw body), listed in the admin
     attention queue. No money moves automatically because the real payload shapes have not been seen yet (reference is read from data.reference,
     data.transaction_reference or data.transaction.reference: UNVERIFIED for refunds/disputes). Revisit once real test-mode events have been captured.
D55. Payouts, ledger flow: request = provider_earnings -> payout_clearing (RESERVED, key payout:<id>:reserved); paid = payout_clearing debit /
     external_clearing credit (payout:<id>:paid); failed or rejected = payout_clearing -> provider_earnings (payout:<id>:returned). A reservation ends exactly
     once (state guards + fixed keys). TWO-PHASE transfer: commit `processing` + deterministic reference `lpo_<payoutId>`, call the gateway OUTSIDE any
     transaction (verify-then-initiate, so re-entry is safe), then apply the result. A gateway error leaves the payout `processing` for an admin to verify;
     a transfer the gateway has never heard of is failed (earnings returned) only by an admin verify after a 10 minute grace. A reversal reported after we
     marked it paid is only FLAGGED (`payout.reversal_after_paid`), never auto-booked. Minimum payout PAYOUT_MIN_MINOR (default 10000). Paystack's transfer
     fee is not yet modelled (platform cost).
D56. Platform admin = allowlist of user ids in PLATFORM_ADMIN_USER_IDS (read per request); everyone else gets 404. EVERY payout needs an admin to approve it
     (no auto-pay at launch). approve/reject/verify are made safe by STATE (a repeat is 409 payout_not_pending), not by Idempotency-Key, because approve
     calls the gateway outside a transaction. GET /admin/attention gathers: amount mismatches, late successes, gateway alerts, failed payouts, reversals after
     paid, stale pending payments, open payouts. A real admin model (roles, MFA, audit UI) is still to build.
D57. Payout accounts: the full account number is never stored (only gateway recipient code, bank code, last 4, bank-resolved name). One per provider; saved
     through the gateway's account resolution. Replacing it pauses payouts for PAYOUT_ACCOUNT_COOLDOWN_HOURS (default 24; an account-takeover control) and is
     refused while a payout is pending/processing. Recipient type is "nuban" (Nigeria only): other markets need other recipient types before launch there.
     Provider identity/KYC verification (PRD §125) is NOT built: until it is, admin approval is the control.
D58. Reconciliation (`npm run reconcile [days]`) is read-only and exits 1 on any disagreement; the comparison is a pure function (payments/reconcile.ts).
     It lists the gateway's transactions (adapter `listTransactions`, unverified against the live API) and compares to payments + capture ledger entries.
D59. Provider trades (`provider_services`, existing table): `PUT /providers/me/services { categories: [canonicalKey] }` REPLACES the list; unknown keys are 400 `unknown_category`.
     `GET /providers?category=<canonicalKey>` matches by canonical key, never by display name (PRD §24); `q` still searches name/headline. Each directory row carries its `categories`.
     No new tables or migrations. Ordering is still alphabetical: real ranking (PRD §38, §96) is Phase 4.
D60. Pre-award conversation = one thread per (task, provider), so invited providers never see each other's chat (PRD §34). It reuses `conversations` with context_type `private` and
     a deterministic uuid (sha1 of task id + provider profile id) as context_id, because D11's `quote`/`task` contexts would either mix providers or need a quote to exist first.
     DEVIATION from PRD §31 (Task Chat / Quote Chat contexts): revisit when assignments exist and move to task/quote contexts. Messages store original text + language only; no translation yet (PRD §29, Phase 2).
D61. Endpoints (`src/api/thread-routes.ts`): `GET /tasks/:id/invitations` (manager only), `GET|POST /tasks/:id/messages[?provider=]`. Managers must name the provider; a provider gets their own thread.
     Not invited = 404 (D21), project member who is not a manager = 403. Sends go through `runIdempotent`. Chat is NOT written to the activity stream (PRD §137). Phone numbers are never released here (PRD §99).
D62. Web: Find searches by canonical key when the trade is a seeded one; the provider the person tapped is remembered in sessionStorage (`lp_pref_provider`, one hour, used once) and offered as a one-tap invite
     on the project page. Providers pick trades at signup and in Profile. The thread polls every 10 s: a stopgap, revisit for PRD §110 (low bandwidth) with push/long-poll.
D63. Quote form sends labour/materials/transport lines only; the server still computes every amount (D29). Money is entered in major units and converted with the currency's own decimals (D4); amounts above
     ~9e15 minor units are refused client-side. Status: written session 11, `test:threads` 5/5; the UI itself has not been through an automated test.
D64. Change requests (PRD §58-60), `src/api/change-routes.ts`: `POST /projects/:id/changes` proposes (status `proposed`; `draft`/`under_review` stay unused), `GET /projects/:id/changes` lists,
     `POST /changes/:id/accept|reject|withdraw`. Accepting applies the change in the SAME transaction: status `accepted` then `applied`, a new `project_baselines` row, `projects.current_baseline_version` + 1.
     The state table is `CHANGE_TRANSITIONS` in `src/engine/state-machines.ts`. Cost and schedule must agree with the effect (increase > 0, reduction/credit/partial_cancellation < 0, no_cost = 0); currency is always the project's (D30).
D65. Who answers a change: the OTHER side. A manager's change that involves a provider is answered by that provider; a provider's change is answered by any manager (never the proposer).
     A change may involve work of at most ONE provider (`one_provider_per_change`), so no per-party approval table is needed. A manager's change on tasks with no live assignment has no counterparty:
     any manager, the proposer included, may accept it. A provider may only propose changes on tasks where they hold an accepted/active assignment. Completed or cancelled tasks cannot be changed.
D66. Baselines: v1 is captured the first time a change is proposed (snapshot of tasks + budget, `capturedBy: first_change_proposal`), because convert never created one. LIMITATION: v1 is therefore "scope when the first
     change was proposed", not "scope at award". Each accepted change adds vN+1 and records which change made it. A change proposed against baseline N cannot be accepted once N+1 exists (409 `baseline_changed`): re-propose.
D67. Financial effect of an applied change: `project_budgets.approved_minor` moves by the signed amount when an approved budget exists (it may not go below 0). Milestones, quotes, payments and the ledger are NOT adjusted
     automatically; the manager adjusts those through their own flows. The delta is recorded in the baseline snapshot and the activity stream (PRD §60 "links directly" is only partly met: see PRD_COVERAGE.md).
D68. Not built for changes: Change Request Chat (PRD §31) and the `draft`/`under_review` states. Schedule changes are stored as `scheduleDeltaDays` only (there is no scheduling engine yet).
D69. Reviews (PRD §91-92), `src/api/review-routes.ts`: only a project manager can review, only a provider who COMPLETED work in that project (assignment status `completed`), once per (project, reviewer, provider) (409 `already_reviewed`),
     1-5 on up to five dimensions, at least one required, optional comment. `GET /projects/:id/reviews` lists reviewable providers; the web shows a panel only when there is someone left to review.
D70. `GET /providers/:id/reviews` returns count, per-dimension averages and recent comments, never the reviewer. No minimum-group threshold yet (PRD §121 applies to government analytics, not to this per-provider view).
     Customer reputation (PRD §93) is NOT built.
D71. No hard-coded currency: `GET /providers/banks` without `?currency=` uses the signed-in user's market default currency, and returns 400 `currency_required` if the user has no market. Payouts themselves remain Nigeria-only (D57).
D72. Notifications (PRD §112-113): `src/lib/notify.ts` writes `in_app` rows INSIDE the caller's transaction (a rolled-back action never notifies), skipping the actor. Rows hold a machine `kind` and ids; the wording lives in
     `web/src/pages/Notifications.tsx` so it can be translated per user language later. Kinds today: task.invited, quote.submitted, quote.accepted, message.received, change.proposed, change.accepted, change.rejected, review.received.
     API: `GET /notifications`, `POST /notifications/:id/read`, `POST /notifications/read-all`. The web polls the unread count every 30 s. Push, email, SMS, quiet hours and channel preferences are NOT built.
D73. Sign-up reads markets from `GET /reference` (a country picker appears when more than one is active); the web no longer carries a default market or a Lagos timezone fallback (UTC is the last resort).
D74. Evidence files (PRD §66-67, §110): `POST /tasks/:id/evidence/upload-url { kind, mimeType, sizeBytes }` returns `{ storagePath, upload }` after the same checks as adding evidence (provider holding the live assignment, or inspector/supervisor;
     task accepted or in progress; project open). Paths are `projects/<projectId>/evidence/<uuid>.<ext>`. Allowed: photos (jpeg, png, webp, heic) up to 15 MB, video (mp4, mov, webm) up to 100 MB, documents (pdf) up to 20 MB,
     receipts (photo or pdf) up to 20 MB. The device PUTs the file straight to storage; nothing large passes through the API. Needs the storage setup from D40 (Supabase bucket) or `STORAGE_DRIVER=memory` in tests.
D75. Adding the evidence row (`POST /tasks/:id/evidence`) now VERIFIES paths issued by upload-url: the object must exist in storage (409 `upload_missing`) and the stored size replaces any size the client claimed. Metadata-only evidence
     and older paths are accepted exactly as before. `GET /tasks/:id/evidence` adds a `url` per file: a signed link valid for 15 minutes (null if storage is unavailable). The web hashes photos and documents up to 20 MB (SHA-256)
     where the browser allows it; the hash and the file's last-modified time are metadata, not proof (PRD §67).
D76. Project timeline (PRD §68, §137): `GET /projects/:id/activity?limit=&before=` is read-only, newest first, cursor-paged. Non-provider members see the whole project; a provider-only member sees events on their own tasks
     (and evidence tied to them) plus what they did themselves, so other providers' quotes and prices never appear (PRD §34). Chat is not part of it. The web hides technical events (`task.transitioned`, gateway and payment
     internals) and words the rest per event type, ready for translation later.
D77. Task work screen (`/projects/:projectId/tasks/:taskId`, PRD §65): the provider starts work, adds evidence, submits; the owner approves, sends back (reason required) or marks complete. Only the existing task-work API is used
     (D41-D44), so no new rules. The project page links to it from every task that has been accepted or later.

    Why: before this an unfunded stage could be submitted and approved and then never funded (payment creation requires `pending`), leaving it unpayable.
    "Where applicable" (PRD §49, Path A) means a per-market switch could later turn this off for markets without protected payment; not built. Status: implemented; tests use `forceFunded` (src/api/test-fund.ts).
